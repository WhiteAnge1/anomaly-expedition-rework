# Roadmap до публичного релиза

Текущее состояние: основная механика, normal T1 smoke, T1/T2/T3 forced loot/empty, enemy squad lifecycle, exact-маркеры, save/load, cleanup, artifact spawn guard и три rescue-класса имеют полевые либо исполняемые доказательства. Переменные локационные counts утверждены и реализованы; следующий тест не активирован.

## 1. Закрыть оставшиеся полевые проверки

1. Провести обычный debug-off прогон T2 в Тёмной лощине: проверить сохранённый roll `5..9` по профилю `5/20/47/26/2%`, совпадение requested/created/captured/linked, радиусы `150..240 м`, loot `offset <= radius/5` и proximity-засаду только если enemy естественно выбран.
2. На save/load или same-level travel подтвердить отсутствие повторного броска и повторного stock spawn при сохранённом `spawn_invoked`.
3. Затем провести обычный debug-off прогон T3 в Мёртвом городе: проверить roll `4..7`, радиусы `140..220 м`, loot `offset <= radius/10`; enemy squad там, как и на T1, создаётся сразу при старте.
4. Один финальный release-candidate smoke с normal config: существующее сохранение, новая вылазка, выход и повторная загрузка убежища; forced/debug-параметры должны оставаться выключенными.

Новые forced-loot/forced-empty и повтор T1 не требуются. Пользовательские artifact/loot/enemy exact-маркеры и их reload/pickup/open/commander-death lifecycle приняты.

Количество настоящих артефактов теперь берётся из утверждённых локационных профилей реворка; stock `4/8/6` остаётся fail-closed fallback. Ложные области бросаются отдельной независимой системой.

## 2. Принять proactive artifact hold в поле

Продуктовое решение принято: все новые raid-artifacts статичны до подбора. После guarded server spawn X-Ray нормализует pivot к поверхности; schema 8 валидирует этот surface envelope, однократно поднимает exact client object через `force_set_position(pos, true)` на `2.0 м` (конфиг `0.5..3.0`), верифицирует и фиксирует только свободные physics elements. Save/load повторяет lift+fix без action counters. ALife teleport, respawn и reactive rescue запрещены.

Перед заморозкой обязателен узкий прогон `docs/FIELD-TEST-PROACTIVE-HOLD.md`. Старый rolling/underground/origin код остаётся только изолированным legacy/debug слоем и не является основанием считать новый путь проверенным.

## 3. Заморозить release candidate

- выбрать следующую версию и обновить её во всех runtime/FOMOD/meta/docs местах;
- зафиксировать normal config без forced-параметров;
- выполнить полный `static_check`, Lua 5.1/LuaJIT, XML/CP1251, watcher self-test и `git diff --check`;
- сверить source и установленную MO2-копию по SHA-256.

После заморозки допускаются только blocker-fixes с повторной проверкой затронутого сценария.

## 4. Завершить документацию

- краткое описание для обычного игрока: что меняется в вылазках и что остаётся штатным;
- подробное описание для опытного игрока: типы областей, награды, enemy/loot/empty, артефакты/классы/мутации, настройки;
- установка через MO2, приоритеты, обновление поверх alpha, удаление и возврат к исходному поведению;
- совместимость и требования к RVM/GRA Bolt/Arrival/PAW;
- debug-guide, известные ограничения, troubleshooting и changelog.

## 5. Проверить установку и обновление

На копии профиля MO2 проверить два пути:

1. чистая установка архива в новый мод с ожидаемым именем и версией;
2. обновление с текущей `0.2.1-alpha` без потери пользовательского конфига и без старых runtime-файлов.

После каждого пути: запуск существующего убежища, новая вылазка, отсутствие FATAL/ошибок мода, корректное отключение/удаление.

## 6. Собрать и опубликовать

- собрать воспроизводимый MO2/FOMOD-архив;
- записать SHA-256 архива и перечень файлов;
- создать Git tag и GitHub release с changelog, инструкцией и исходниками;
- после отдельной отмашки пользователя загрузить тот же проверенный архив и инструкции на Google Drive;
- проверить обе ссылки и совпадение SHA-256 скачанных файлов.

Публичный релиз считается готовым только после полевых пунктов 1, решения из пункта 2 и успешной clean-install/upgrade проверки.
