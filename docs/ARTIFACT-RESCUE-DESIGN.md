# Проект безопасного спасения рейдовых артефактов

Статус: backlog. В этой итерации runtime-перемещение намеренно не реализовано. Штатные количества `4/8/6` также не меняются до полевой оценки доступности после будущего rescue.

Подробный аудит фактической цепочки, zone-aware критерии, доступные API, координаты курсора карты, три механизма и сохраняемая state machine находятся в `docs/ARTIFACT-RESCUE-RESEARCH.md`. Этот ранний проект сохранён как краткая исходная постановка; при расхождении приоритет имеет новый исследовательский отчёт. В частности, `(0,0,0)` сам по себе не доказывает ошибку: X/Z-ноль входит в terrain-прямоугольник каждой из трёх рейдовых карт.

## Фактический путь RVM

Источник в сборке: `GRA Bolt/gamedata/scripts/raid_anomalys.script`.

1. `spawner_anomals_zones(level_name)` выбирает прямоугольник terrain, создаёт `gen_pos` с `y=0`, получает `lvid = level.vertex_id(gen_pos)` и для валидного центра вызывает `spawner_anomals`.
2. После создания аномальной зоны вызывается `spawn_artefact_in_zone(anom_zone, gen_pos, level_tier)`.
3. `shift_vector_for_artefacts` до 20 раз смещает X/Z и проверяет только попадание в один из terrain-прямоугольников.
4. Затем код получает `lvid = level.vertex_id(gen_pos)`, но **не проверяет** его против невалидного `4294967295`, хотя соседние пути создания аномалий такую проверку выполняют.
5. Позиция без дополнительной валидации становится `gen_poss = level.vertex_position(lvid)`, после чего вызывается `alife_create_item(section, {gen_poss, lvid, actor_game_vertex})`.
6. Возвращённый ID сохраняется в локальной `raid_current_anomaly_zones[lvid].artefact_id`; таблица сохраняется через callbacks `save_state/load_state` и используется при `release_raid_zones`.
7. `raid_artefacts.script` отдельно оборачивает этот spawn и ставит server object в сохраняемую очередь рандомизации класса/мутаций. Эта идентичность не должна теряться при rescue.

Текущий реворк оборачивает только `raid_anomalys.spawn_artefact_in_zone`, поэтому уже получает `anom_zone`, исходный `pos`, `level_tier` и итоговый ID. Это лучшая точка для записи provenance, но не для немедленного безусловного перемещения.

## Классы неисправности и вероятные причины

### A. Исходный `server_pos=(0,0,0)`

Наиболее сильная гипотеза — невалидный `lvid` после второго смещения: `shift_vector_for_artefacts` проверяет terrain rectangle, но не доступность level graph. `level.vertex_position(invalid)` затем даёт нулевую либо неопределённую позицию. Это согласуется с тем, что server object уже при первом снимке находится в world origin.

Будущий детект должен сравнивать не только координаты с нулём, но и provenance:

- объект без parent и на текущем raid level;
- `server_pos` в малом радиусе от `(0,0,0)`;
- переданный в wrapper исходный `pos` существенно дальше от origin;
- сохранённый/повторно вычисленный безопасный vertex около исходной аномальной зоны валиден.

Так исключается ложное срабатывание на карте, где `(0,0,0)` теоретически является нормальной игровой точкой.

### B. Нормальный server-Y, затем online-Y около `-40/-50`

Здесь создание прошло с правдоподобной server-позицией. Скачок происходит при online transition, когда физический предмет получает модель/physics shell и падает через отсутствующую, одностороннюю или ещё не стабилизированную коллизию. Маркер лишь отражает уже изменившуюся позицию.

Детект должен хранить последний достоверный server snapshot и после появления online object требовать одновременно:

- отсутствие владельца (`parent_id` nil/0) и actor/NPC ownership;
- падение Y относительно последней достоверной точки и ближайшей level vertex больше настраиваемого порога;
- стабильность плохого состояния в нескольких обновлениях/не менее заданного времени, чтобы не ловить один переходный кадр;
- X/Z всё ещё относятся к тому же raid artifact lineage.

### C. Уход за играбельную границу, под край/висящий забор

Одного большого смещения недостаточно: обычное катание по доступному склону разрешено. Rescue допустим только при совокупности признаков недоступности, например:

- текущая точка не получает валидный level vertex либо расстояние до привязанной vertex чрезмерно;
- значительный вертикальный разрыв с vertex/геометрией;
- объект устойчиво находится за сохранёнными границами terrain либо намного дальше от исходной аномальной зоны;
- состояние сохраняется несколько секунд и объект не принадлежит NPC/actor.

Положение возле машины, стены или забора само по себе недостаточно. Для случаев «под висящим ограждением» потребуется доказуемый тест доступности; одного X/Z-radius не хватит.

## Предлагаемая архитектура будущего этапа

### Сохраняемая provenance-запись

На успешном wrapper-callback записывать по artifact ID:

- section, исходные `anom_zone/level/tier`;
- переданный RVM `spawn_input_pos`;
- первый валидный server pos/level vertex;
- linked zone anchor/radius после её создания;
- last-good server/online snapshot;
- counters: bad samples, rescue count, cooldown, reason;
- lineage replacement IDs, если они когда-либо появлялись через штатный NPC/recreated callback.

Запись должна войти в schema сохранения реворка и восстанавливаться до периодической диагностики.

### Безопасная rescue-точка

Кандидаты строить от исходного `spawn_input_pos`/первой валидной позиции, а не от текущего провалившегося объекта:

1. валидный `level.vertex_id` и нормализованный `level.vertex_position`;
2. несколько небольших смещений вокруг исходной аномальной зоны;
3. проверка текущего level, вертикального разрыва, terrain bounds и отсутствия явной закрытой геометрии доступными API;
4. ограничение расстояния от исходной зоны, чтобы rescue не превращался в выдачу предмета игроку;
5. диагностический dry-run до включения перемещения.

### Стабилизация и перемещение

Предпочтителен перенос **того же object ID** после перехода online: установить позицию на проверенную точку, обнулить линейную/угловую скорость доступным physics API и повторно проверить через несколько кадров. Нужно сначала подтвердить фактические Lua-методы объекта/physics shell в этой сборке.

Recreate является только крайним вариантом и пока считается небезопасным:

- локальная `raid_current_anomaly_zones` базового RVM недоступна извне и продолжит хранить старый ID;
- `raid_artefacts.saved_artefacts/queued_artefacts` привязаны к object name/ID и несут класс/мутации;
- реворк хранит `artifact_id`, обратный индекс `artifact_zone` и map spots;
- неатомарный release/create создаёт окно для дюпа или потери предмета.

Если same-ID teleport окажется невозможен, нужен отдельный API/патч к базовому RVM для атомарной замены ID и переноса данных, а не скрытая локальная реконструкция в реворке.

## Guardrails

- Никогда не rescue объект с parent actor/NPC/container или подтверждённым ownership.
- Не rescue после закрытия зоны либо после pickup/recreated lineage resolution.
- Не менять section, tier, мутации, стоимость или очередь `raid_artefacts`.
- Не создавать второй предмет до подтверждённого удаления первого; предпочтительно вообще не создавать новый ID.
- Не исправлять обычное катание, если текущая позиция доступна по nav/геометрическим признакам.
- Не более одного автоматического rescue на класс неисправности и малого общего лимита на объект; cooldown и fail-closed отключение после ошибки.
- Все решения сохранять; load не должен повторять уже выполненное перемещение.
- До включения действия иметь режим `observe_only`, который пишет причину, исходную/текущую/целевую позиции и все guardrails.
- Cleanup/настоящий выход освобождает тот же объект штатным RVM; реворк не забирает ownership жизненного цикла.

## План реализации и тестов отдельного этапа

1. Добавить только provenance + observe-only классификатор; собрать новые логи трёх локаций.
2. Подтвердить Lua API same-ID position/physics stabilization на временном тестовом предмете, не на награде.
3. Unit/static: origin требует несогласованность с spawn input; underground требует несколько bad samples; boundary не срабатывает на доступном склоне; parent/closed guards всегда запрещают действие.
4. Поле: искусственно воспроизвести каждый из трёх классов, затем save/load до и после rescue.
5. Проверить NPC pickup, смерть NPC, `actor_pickup_recreated_id`, точный marker и закрытие зоны без второго предмета.
6. Проверить класс/мутации до и после, очередь рандомизации ровно один раз и штатный cleanup.
7. Отдельно проверить обычное катание на Поляне: доступный предмет не перемещается.
8. Только после успешной доступности пересмотреть баланс количества `4/8/6` и провести normal-player рейды с debug off.

## Открытые технические вопросы

- Какие именно same-ID setters позиции и скорости экспортированы текущими modded exes для server и online artefact object?
- Можно ли достоверно проверить collision/line-of-sight или достижимость предмета без дорогого полного path search?
- Достаточен ли `location_level`/nearest vertex для границ всех трёх карт, особенно ограждений?
- Нужен ли небольшой controlled upward offset при стабилизации, и как не вытолкнуть предмет из аномальной сцены?

До ответа на эти вопросы rescue остаётся документированным backlog, а runtime реворка только диагностирует существующие позиции.
